# intl-sourcing-scrape — 해외(중국) 소싱 수집 (수집 방식 ②)

> 실행 = **저장된 코드가 없다.** Claude가 playwright-mcp로 페이지를 열고 **이 문서의 명세대로** 행을 만든다 — 그래서 이 문서가
> 곧 실행 명세다. 품명은 사용자가 주고, 아래 규칙은 품명이 무엇이든 같다. alibaba(로그인 없음)와 1688(로그인 필요)은
> 문이 다르지만 실행 방식이 같아 같은 ②다.
> 산출 = `output/{YYYYMMDD}-{alibaba|1688}-{품명}.csv` (스키마①, `pattern`=②, 국제운임용
> `weight_g`·`volume_cm3` 포함). 열 정의는 `research-output-schema.md` 스키마① — 여기 다시 적지 않는다.

## 준비물

- **playwright-mcp** (Claude Code 의 브라우저 자동화) — `browser_navigate`·`browser_evaluate`·`browser_type` 을 쓴다.
- **1688 계정**: 1688 은 검색부터 로그인을 요구한다. 사용자 본인의 휴대폰 SMS 인증으로 playwright 창에서 **직접** 로그인한다
  (Claude 가 계정·비밀번호를 받지 않는다). alibaba.com 은 로그인이 필요 없다.
- 키워드: 사용자가 준 품명을 **영문(alibaba)·중문(1688)** 으로 옮겨 확인받는다. 예) «스테인리스 육각볼트» → `stainless steel hex bolt` / `不锈钢 六角螺栓`.

## 🔴 시작 전 질문 — 상세페이지를 열기 전에 한 번만

상세페이지를 방문하기 **전에** 사용자에게 묻는다. 여기서 안 물으면 무게만 뽑고 나중에 부피가 필요해져 **같은 페이지를 두 번 방문**하게 된다.

- **"배대지(국제배송 대행) 요금을 받으셨나요? kg 기준인가요, CBM(부피) 기준인가요, 아직 모르시나요?"**
  - kg 기준 또는 미정 → 상세에서 **weight_g**(중량) 위주로 수집
  - CBM 기준 → **volume_cm3**(부피)까지 같이 수집
  - **모르겠으면 둘 다 수집한다** — 같은 페이지에 같이 있는 경우가 많아 한 번에 뽑는 게 재방문보다 싸다
    (1688 «제품 중량» 표는 무게·부피가 같은 행에 있고, alibaba 는 `unitWeight`+`unitSize` 가 같은 JSON 객체에 있다).
- 관세율은 수집에 영향이 없어 이 시점엔 묻지 않는다 — 원가를 비교하는 단계에서 확인한다.
- 바깥 워크플로가 이미 물어봤으면 그 답을 쓴다(재질문 생략).

## 수집 기준 — 검색 상위 상품 30 + 그 30개 전부 상세

alibaba·1688 은 전용 도구가 없어 매번 playwright 로 직접 방문하므로 비용이 든다. 그런데 목록만 있는 행은 규격·MOQ·무게가 비고,
상세를 본 행은 규격형·사다리형으로 쪼개져 행수가 불어난다 — 둘을 한 표에 섞으면 중앙값이 «상세 본 상품»의 옵션 수에 끌려간다.
그래서 **목록 수 = 상세 수 = 30** 으로 맞춘다.

- 목록: 검색결과 순서 상위 30 **상품**. 1688 은 같은 상품이 목록에 두 번 뜨므로 **상품(URL) 기준으로 30** 을 센다.
- 상세: 그 30개 전부. 결과 CSV 의 모든 행이 상세에서 온 값이어야 한다 — 목록만 있는 행을 남기지 않는다.
- 상세 방문 30×2 = 60회. 다른 N(`--top N`)을 쓰려면 사용자에게 먼저 확인한다.

## 순서 — alibaba 먼저, 1688 다음

⚠️ **alibaba 와 1688 은 다른 서비스다.** 같은 계열(중국 공장가·통관·국제배송)이지만 **문이 다르다** — alibaba 는 로그인
불필요, 1688 은 원칙상 SMS 인증(단 브라우저에 기존 로그인이 남아 있으면 생략될 수 있다). 순서가 «alibaba 먼저 → 1688» 인
것은 가격이 아니라 접근 난이도(로그인 불필요 우선) 때문이다. 중앙값 기준으로는 1688 이 더 저렴한 경향이 있다.
⚠️ `WebFetch` 로 `s.1688.com` 을 읽는 것은 안 된다 — 로그인 페이지로 리다이렉트된다. 반드시 playwright 로 연다.

## alibaba.com

```
검색: browser_navigate → alibaba.com/trade/search?SearchText=<영문키워드>
  → 한국어 로컬라이즈 + ₩ 자동 환산. browser_evaluate 로 상품 링크 상위 30개(URL 기준)를 추출한다.
  목록의 가격 노드 정규식 /₩[\d,]+(-[\d,]+)?/, MOQ 는 "최소 주문: N 개" 문구.
상세: product-detail 에서 browser_evaluate 로 window.detailData.globalData.product 를 읽는다 —
    .price.productLadderPrices → 수량구간 사다리 [{min,max,price}] (₩환산) → **있으면 사다리형**
    .sku.skuInfoMap            → 규격 조합별 정보 → **항목에 price 가 있으면 규격형**
    .sku.skuAttrs              → 규격 축 이름·값("색상"×"크기" 등) — 행의 spec 문구를 만든다
    .moq / .quantityUnit       → 상품 MOQ·단위(단일 숫자. 사다리형이면 최저 구간 min 과 같다)
  ⭐ 원통화 = 달러: 사다리 구간 항목과 SKU 항목 둘 다 `price`(₩ 환산 표시가)와 `dollarPrice`(달러 원가)를 같이 갖는다.
     → unit_price_krw = `price`(₩) · **currency_orig = USD · price_orig = `dollarPrice`**.
       ₩ 표시가는 alibaba 가 그날 환율로 환산한 값이라 재수집마다 흔들리고, 달러가가 실제 견적 기준이다.
     SKU 에 `promotionPrice`(한시 할인가)가 있으면 단가로 쓰지 않는다 — 상시가 `price` 를 쓰고 effective_cost_note 에
       «프로모션가 ₩N(한시)»로만 남긴다(할인 종료 뒤 원가가 조용히 오르는 것을 막는다).
  ⭐ 두 모델은 배타적으로 나타난다: 사다리가 있으면 skuInfoMap 에 price 가 없고, skuInfoMap 에 price 가 있으면 사다리가 없다.
     둘 다 있거나 둘 다 없으면 미관측 케이스 — **사용자에게 확인**하고 임의로 규격×구간을 곱하지 않는다.
  🔴 **가격이 달라지는 축마다 행을 쪼갠다 — 1행에 범위를 우겨넣지 않는다.**
    ⛔ price_orig/unit_price_krw 에 "min-max" 범위 문자열을 넣지 않는다(한 행 = 단가 하나).
    ⛔ spec 도 같은 원칙 — 규격이 여러 개면 "M3.5-M12"처럼 한 칸에 뭉치지 않고 규격 수만큼 행을 쪼갠다
       ("6-12"(mm)처럼 값 자체에 하이픈이 있는 원자적 규격값은 금지 대상 아님).
    (a) **사다리형 → 수량구간 수 × 규격(SKU) 수만큼 행.** 규격도 항상 쪼갠다 — "규격 4종 공통가"처럼 **개수만** 남기면
       실제 규격이 뭔지 CSV 에서 사라져 원본 페이지를 다시 열어야 한다. 각 행 price_orig/unit_price_krw = 그 구간 단가
       (규격이 달라도 같은 구간이면 같은 값이 규격 수만큼 반복된다), **moq = 그 구간의 min**(상품 공통 MOQ 를 전 행에
       복사하지 않는다 — 뒷단은 «그 행의 moq»를 발주수량으로 읽는다). spec = `{skuAttrs 의 실제 규격값}(수량구간 N개~)`.
       사다리 전체(전 구간표)는 effective_cost_note 에 남긴다.
       ⚠️ 행수가 늘어난다 — 규격 M종 × 구간 N개 = M×N 행. 같은 가격이 규격 수만큼 반복되는 것은 정상이다
       (건수·중앙값을 셀 때는 같은 상품·같은 수량구간·같은 단가를 1건으로 접는다 — `research-output-schema.md` §행 분리 기준).
       예) moq=100 · 규격 4종(9mm/12mm/15mm/19mm) · [100~9,999 ₩70 / 10,000~99,999 ₩56]
           → 8행: (9mm,₩70,moq=100)·(12mm,₩70,moq=100)·(15mm,₩70,moq=100)·(19mm,₩70,moq=100)·
                  (9mm,₩56,moq=10000)·(12mm,₩56,moq=10000)·(15mm,₩56,moq=10000)·(19mm,₩56,moq=10000)
    (b) **규격형 → 규격(SKU) 조합 수만큼 행.** spec=`{조합명}(SKU)`, 단가=그 SKU 의 price,
       **moq = 상품 MOQ 그대로**(규격이 바뀌어도 최소수량은 안 바뀐다).
       예) moq=10 · 13조합 → 13행 전부 moq=10, 단가만 조합별(₩504 … ₩3,052).
  무게·부피: globalData.trade.logisticInfo 의 unitWeight / unitSize → weight_g / volume_cm3 (시작 전 질문의 답에 따라).
```

## 규격 단위 mm 로 맞추기 (alibaba·1688 공통)

규격 구간 비교는 **mm 가 붙은 치수만** 읽는다(`18-32` · `M8` · `2inch` 는 «규격 미상»으로 빠진다). 읽는 쪽을 느슨하게
하지 않고 **수집할 때 spec 값을 고친다.** 변환한 값을 앞에, 원래 표기를 괄호로 남긴다.

1. **단위 없는 범위 `N-M`** — **축 이름이 치수**(크기·규격·사이즈·폭·직경)일 때만 mm 를 붙인다: `18-32` → `18-32mm`.
   앞 숫자가 뒤 숫자보다 크면(«26-12 ---- 800») 범위가 아니다 — 안 붙인다.
   - alibaba: skuAttrs 의 축 이름이 근거다.
   - 1688: 축 이름이 늘 «사양(规格)»이라 근거가 못 된다 → 상세에 **«직경 범위/直径范围» 표·속성이 있는 상품만** 1~3자리 범위에 붙이고
     비고에 «규격 단위 mm ← 상세 «직경 범위» 표»를 남긴다. 근거 없는 상품·네 자리 범위(«600-1300»)는 안 붙인다.
2. **미터 나사 `MN`** = N mm: `M8` → `8mm(M8)` · `M3.5` → `3.5mm(M3.5)`.
   ⚠️ 나사 굵기이지 조임 지름이 아니다 — 비고에 «나사 호칭»이라고 남겨 구간 비교에서 가려 읽을 수 있게 한다.
3. **인치** = ×25.4, 소수 첫째 자리(반올림): `2inch` · `2"` · `2인치` → `50.8mm(2inch)` · `1-2inch` → `25.4-50.8mm(1-2inch)` ·
   분수도 같다 `3/4인치` → `19.1mm(3/4인치)`. ⚠️ 분수를 통째로 읽는다 — `3/4인치` 에서 «4인치»만 떼어 읽지 않는다.

비고(effective_cost_note)에 근거를 적는다 — «규격 단위 mm ← 축 «크기»» · «M8=8mm(나사 호칭)» · «inch×25.4».
⛔ **단위 없는 숫자 하나**(«2» · «5»)·**단위 없는 분수**(«5/8» · «1-3/4»)는 mm 인지 inch 인지 페이지에 근거가 없다 — 고치지 않고
   그대로 둔다(추정 금지). «1-3/4»는 대분수라 범위가 아니다 — «1-3mm/4»로 만들지 않는다.
⛔ 유형·색상 값(«실버» · «육각»)에는 아무것도 붙이지 않는다. 품목이 바뀌면 축 이름·근거 열 이름부터 다시 확인한다.

## 1688

```
로그인: 먼저 로그인 없이 s.1688.com 접속을 시도한다. 로그인 페이지로 튕기면 그때 사용자에게 playwright 창에서
  SMS 인증(휴대폰) 로그인을 요청한다. 브라우저에 이전 로그인이 남아 있으면 인증 없이 바로 검색 결과가 뜬다.
  이메일/비밀번호 로그인은 실패한다(账密错误) — SMS 로만.
검색: 검색창 `#alisearch-input` 에 중문 키워드를 **직접 타이핑해** 제출한다.
  ⚠️ 중국어 키워드를 URL 파라미터에 직접 넣지 말 것 — 인코딩 불일치로 결과가 0건이 된다.
  ⚠️ 다른 text 입력칸에 넣으면 로그인 화면으로 튕긴다(로그인 만료로 오인하기 쉽다).
  목록은 접근성 스냅샷 대신 `browser_evaluate` 로 상품 링크만 추출한다(같은 상품이 두 번 뜨므로 URL 기준 30).
  🔴 **MOQ·규격·무게는 목록에 없다** — 상세페이지(`detail.1688.com 나온다. 목록 텍스트로는 규격 5%, 무게 0%.
상세: browser_evaluate 로 window.context.result.data 를 읽는다 —
   - `.Root.fields.dataJson.skuModel.skuInfoMap` = {규격명: {price, discountPrice, isPromotionSku}} → **price 가 있으면 규격형**
   - `.mainPrice.fields.priceModel.currentPrices` = [{beginAmount, price}] ·
     `.mainPrice.fields.finalPriceModel.tradeWithoutPromotion.offerBeginAmount` = 상품 MOQ
     ⚠️ 규격형에선 currentPrices 가 사다리가 아니라 **최저·최고 단가 2줄**이다(beginAmount 가 같다).
        skuInfoMap 의 price 가 전부 비어 있을 때만 사다리형(공통가)으로 읽는다.
     ⚠️ beginAmount 가 600·2000 처럼 섞여 나오고 단가가 수량과 같이 오르는 상품이 있다 — 의미 미확인.
        moq 는 offerBeginAmount 를 쓰고 비고에 «⚠️ 수량조건 혼재 — 의미 미확인»을 남긴다.
   - 단가 = 상시가 `price`. `isPromotionSku` 이고 `discountPrice` 가 다르면 비고에 «프로모션가 ¥N(한시)»로만 (alibaba 와 같은 원칙).
   - 행 분리는 alibaba 와 같다: 규격형 → 규격 수만큼 행(spec=`{규격}(SKU)`, moq=상품 MOQ), 사다리형 → 구간 × 규격만큼 행
     (moq=구간 하한, spec=`{규격}(수량구간 N개~)`) — «규격 3종 공통가»로 뭉치지 않는다.
   - MOQ 를 화면 문구에서 읽어야 할 때: 상품마다 표현이 다르다("1개부터 도매 가능" / "최소 10개 주문" / "최소 1개부터 구매 가능")
     → 정규식 `(?:최소\s*)?([\d,]+)\s*개\s*(?:부터|이상)?\s*(?:도매|구매)?\s*가능|주문`.
   - 무게·부피는 화면의 «제품 중량» 표(규격|길이|폭|높이|부피(cm³)|무게(g))에서 규격명으로 맞춘다 — 표가 없는 상품은 공란(추정 금지).
   - 환율: 목록 카드가 띄우는 «¥x ≈₩y» 에서 읽는다(¥0.3 미만은 반올림 오차가 커서 제외, 중앙값). 원통화 = CNY, price_orig = ¥.
     비고에 «환율 ¥1≈₩N(1688 화면 환산 중앙)».
   - 번역이 안 걸린 상품(중국어 그대로)은 상품명은 목록의 한국어 제목을, 규격명은 원문을 유지하고 비고에 적는다.
예비 경로 — 데이터 객체를 못 읽을 때: 화면에 보이는 HTML 표를 browser_evaluate 로 텍스트 파싱한다.
   - 규격마다 단가가 다른 표 → 규격형 / 수량구간별 단가 표("阶梯价": N개 이상 ¥x) → 사다리형. 행 분리 규칙은 위와 같다.
   - 두 표가 다 보이면 미관측 케이스 — 사용자에게 확인, 임의로 규격×구간을 곱하지 않는다.
```

## 공통 규칙

- 한 행 = 단가 하나. 범위 문자열·나열 금지. 규격이 여러 개면 규격 수만큼 행.
- 데이터가 없는 칸은 **공란**으로 둔다 — 상품명에서 추정해 채우지 않는다.
- **상세를 못 본 상품은 비고에 표시한다** — «Product Not Available»·로딩 실패 등으로 상세를 못 읽은 상품은 목록값(가격·MOQ)으로
  1행만 남기고 effective_cost_note 에 «⚠️ 상세 조회 실패(목록값 — 규격·수량구간 미확인)»을 적는다. 스키마 열은 늘리지 않는다.
- 중간 원자료(JSON 등)는 세션 임시 폴더에 두고 저장소에 남기지 않는다.
